# Architecture and extension guide

MathRacer is a code-only Godot 4.7.2 .NET project. The root node in `Main.tscn` runs the `Game` script. C# generates the world, illustrations and interface at startup. Player-facing text is Czech.

## Source layout

A folder under `Scripts` is a namespace: `Scripts/Saves/SaveStore.cs` is in `MathRacer.Saves`. The names are chosen so that
no namespace has the name of a type (`World`, `Village` and `Game` are classes, hence `Valley`, `Settlement` and `App`), and
`contract-checks` fails when a file is in the wrong namespace, lies loose in `Scripts`, or a namespace clashes with a type.
A class that is written in several files (`Game`, `GameUi`, `World`, `Village`, `BuildProject`, `Works`, `HousePlot`) has all its
parts in the folder of the class, with one exception: `Diagnostics/Game.Diagnostics.cs` is a part of `Game` and so is in
`MathRacer.App`, which is why it can be left out of the release build together with its folder.

| Folder (namespace `MathRacer.<folder>`) | What lives there |
| --- | --- |
| `App` | `Game` and every `Game.*.cs`, `Texts`, `Interaction`, `GameControls`, `Settings`, `LaunchOptions`, `GameState` |
| `Ui` | `GameUi` and every `GameUi.*.cs`, `UiIntent`, `DeliveryPicture`, `TaskMarker` |
| `Graphics` | `Art` (procedural meshes and icons), `Obstacles` (collision helpers), `Celebration` |
| `Quizzes` | `IChallenge` and the generators of the four kinds of question (`Mathematics`, `Letters`), `QuizType`, `QuizSession` |
| `Saves` | `SaveData` and its sections, `SaveDataV4`, `SaveRules`, `SaveMigrations`, `SaveStore`, `PostcardProgress` |
| `Valley` | `World` and every `World.*.cs`, the terrain, roads, river, vegetation, grass, weather, wildlife |
| `Settlement` | `Village` and every `Village.*.cs`, `HousePlot`, `PlotPlans` |
| `Buildings` | `BuildProject`, `BuildPlans`, the mill, the tower, the jetty, the ford, the boat, the works |
| `Tasks` | `HaulTrip`, `ITripTarget`, `Expedition`, `RouteGuide`, `TaskSlot`, `DrivingEvents` |
| `Vehicles` | `Vehicle`, `VehicleModel`, `FollowCamera`, `WheelTracks`, `Trailer` |
| `Garage` | the car items and looks (`Customization` of old), `CarRewards`, `Economy` |
| `Characters` | `Character`, the roles, `ActorIds`, `CharacterCatalog`, the companions and the golem |
| `Diagnostics` | the headless checks, the capture views and `DiagnosticSuites` |

The namespaces depend on one another in both directions (every one of them can reach every other), mostly because `Settings`,
`GameState` and the constants of `Game` live in `App`. `docs/REFACTORING_PLAN.md` lists what a first step towards layers would be.

## Module boundaries

| Module | Responsibility |
| --- | --- |
| `Game` and its feature partials | Compose the scene, handle input and state transitions, coordinate activities and restore the active panel. The state that more than one feature shares is in four small objects that hold no scene nodes: `Interaction` (the state, the state before a pause, the character the player is talking to), `QuizSession` (which quiz kinds are on, the seeded generators, the open question, the wrong answers and the trip that waits for it), `TaskSlot` (the one delivery, collection or trailer trip under way, and how a new one replaces it) and `Economy` (coins, owned garage items, the coins of the open reward panel). `Game` keeps the properties its features already used (`State`, `Delivery`, `Haul`, `CurrentChallenge`, `Coins`), which forward to them. Per-frame work is a list (`Game.Systems.cs`, `RegisterSystems`) and the panel of each interaction state is registered in `Game.Panels.cs`; a new state or tick is added there, and `contract-checks` fails when an interaction state has no panel. |
| `ActorRole` and its subclasses (`ActorRoles.cs`) | Give each character one role: roadside friend, house resident, trader, witch, sorcerer or collector (farmer, gardener, gem collector, toymaker). A role picks the `Game` flow for talking to the character and for its solved quiz, and supplies its marker icon and talk hint. Every builder, source and works role has an icon of its own, drawn as a vector outline by `Art.RoleTaskIcon`; sites without a worker (the sand pit, every second site) and the two driving courses put the same kind of icon on a `TaskMarker`. New character types add a role instead of new `Is…` checks in `Game`. |
| `CarRewards` and `RoadsideProgress` | Hold the owned garage items and the player's coins that buy them (prices live on `CarReward`), and which roadside friends have unlocked or finished their expedition. `WorldCoins` scatters collectible coins along the roads; their positions are not saved. `Game` owns one of each and saves them. |
| `GameUi` and its feature partials | Build panels and HUD elements, manage menu focus and emit player intents. The partials are split by area (`Input`, `Challenges`, `Residents`, `Garage`, `Hints`, `DeliveryHud`, and one per feature); a button never calls the game, it sends a `UiIntent` through the single `Intended` event and `Game.HandleIntent` (`Game.Intents.cs`) is the one switch that answers it. A new button is a new `UiIntent` record and a new case there. |
| `Texts` | The fixed Czech texts of `Game*.cs` and `GameUi*.cs` as constants (names made from the text without diacritics). Texts with values inside are methods (`Texts.AnimalsLeft(remaining, total)`). The texts of data tables (`CharacterCatalog`, `Works`, `Village.*`, the word lists of the questions) stay next to the colours and numbers of their entry. |
| `World`, `WorldLayout` and `Village` | Generate seeded routes, plots and interactive actors. `World` registers actors under stable save IDs and exposes them for proximity checks and placement. Names, greetings and colours of recurring characters live in `CharacterCatalog`; its order assigns actor IDs. |
| `LaunchOptions` and `Settings` | `LaunchOptions` is the only reader of the command line. `Settings` holds tuning constants and the only state that outlives a scene reload: the world seed and the quiz settings carried into a new game. |
| `Terrain`, `Roads`, `RoadGrading` and `River` | Provide elevation, road surface and clearance data for meshes, collision, placement, navigation and driving. |
| `Vehicle`, `FollowCamera` and `VehicleAppearance` | Handle movement, camera and cosmetic state. `VehicleModel` shares geometry between gameplay and garage previews. |
| `Expedition` and `DrivingEvents` | Handle cargo and vehicle courses. |
| `RouteGuide` | Plans the road route to one target and owns the road arrows and the final off-road arrow. Expeditions and ford trips each create one. |
| `Trailer`, `Ford`, `BuildProject` and `World.Ford.cs` | The towed trailer follows the car's hitch along `World.DriveSurface` without collision of its own; it is lent for every trip and won as the bridge's reward. `BuildPlans` lists the ten deliveries of each of the four buildings. `BuildProject` holds the stage; `Ford` (the bridge) is one, its deck becomes solid after the tenth. `World.PlanFord` plans the ford, its sand pit, quarry and clay pit and the beaver. `Game.Ford.cs` runs the trips, which share the single task slot with expeditions (`Game.TaskActive`). |
| `HaulTrip`, `Works` and `World.Works.cs` | `HaulTrip` is one trailer trip (source, loading question, drop ring) for an `ITripTarget`: a `BuildProject` (a building), a `Works` (raw material), a `HousePlot` (a building plot) or a `HouseTripTarget` (a house's planks or bricks). The target gives the load, the drop ring and the contractor, and does what the finished delivery does (`FinishDump`); `Game.Trips.cs` starts every trip (`StartTrip`) and carries on from the quiz that comes before it (`StartDeparture`). A new kind of trip is a new target, one name in `TripKinds` and a way to find it again from a save (`Game.TripTarget`). `World.PlanIndustry` places the log yard and three `Works` (sawmill, brickworks, gravel works; `WorksCatalog` holds what each takes in and makes). The works first try the village edge (`World.WorksBand`, measured with `Village.PlotDistance`, which the quiet belt around the houses would otherwise forbid) and fall back to passes that relax their spacing, slope and road rules until all fit. `World.PlanExtraSources` then adds a second site for each raw material (`ExtraSources`, at least 110 m from the first); `HaulTrip.Source` is the nearest site when the trip starts and `World.SourceSites` lists them all, so an empty trailer is loaded at whichever one it reaches, and the trip adopts the site it reached. Each second site has a worker (`SourceRole` for the load, IDs 54–57 for stones, soil, sand and logs; the sand pit's worker sends the sand to the glassworks and asks the bridge's loading question): `World.PickupActor(load, source)` names whoever asks, and `World.AskerIds` lists the IDs a saved loading question may come from. The quarry, clay pit and log yard have workers (`SourceRole`, IDs 51–53) who start supply trips and ask the loading question; each works has a worker (`WorksRole`, IDs 45–47) who shows the stock and loads goods. A stock of up to 12 units is shown one stack or heap per unit. `Works.Take` is how a building takes goods. |
| `SitedProject`, `Mill`, `Lookout`, `Jetty` and `World.Builds.cs` | The mill, lookout tower and jetty are `SitedProject`s: each stands at a `BuildSite` (unloading ring, road point, direction, builder spot) and has ten stage nodes, with solid parts that only block the car once built. `World.PlanBuilds` picks the sites (the tower and mill try the band near the village, `World.LandmarkBand`, preferring high ground and short distance, then anywhere; the jetty a gentle bank) with a way from a road, in passes that allow deeper cuts. `PlanWay` keeps the way within `PathMaxGrade` by cutting it into the slope; `Terrain.Grade` applies the cuts before anything is placed on the terrain, so `PlanFord` plans everything first. Builders (`BuilderRole`, IDs 44 and 48–50) give the work. The special last load comes from a collector, whose quiz loads it (`Game.CompleteChallenge`). `Game.Rewards.cs` holds the completion rewards (coins, the garage items from `CarAccessory.FlourSack`, `CarAccessory.Binoculars` and `CarLook.Water`, the baker's bonus and the mill's sails); `Game.Lookout.cs` the look from the tower (`FollowCamera.ShowPanorama`, `WorldCoins.Flash`, `Character.Ping`); `Boat` the jetty's boat. The jetty's duck is a `CollectorPet` of kind `Duck` owned by the world (`World.Duck`, `World.AllPets`), whose count is the jetty's stage. |
| `HousePlot`, `PlotPlans` and `Village.Plots.cs` | The village has six building plots (`PlotPlans.Count`). `Village.GeneratePlots` runs last, after the square and before the architectural details, so the rest of the village keeps its old positions: it lists lots beside every road, nearest to the village centre first, takes the first six that are clear (`PlotIsClear`: off roads and the river, clear of everything reserved so far and of the roadside benches and signs) and reserves it (`IsReserved`, so trees and later placement avoid it). It tries ground inside the village's existing terrain platform first and leaves the shared `plots` list alone, so the platform and the search for the works and landmarks are unchanged. `HousePlot` is one lot: a staked-out site with a newcomer (`PlotResidentRole`, actor IDs from `World.FirstPlotResidentId`, `CharacterCatalog.PlotResidents`) and six stage nodes (slab, lower walls, upper walls, roof frame, roof, finishing), with solid parts that block the car once built. `PlotPlans.CargoOf` lists the six loads (gravel, two of bricks, three of planks), always goods from a works. A plot's trip is a `HaulTrip` whose drop ring lies in front of the lot, on a walkway to the street; `Game.Plots.cs` runs it in state `PlotStatus`, shares the task slot with the other trailer trips, sends the player for raw material when the works is empty (`BeginMissingSupply`) and, after the sixth load, pays `PlotCoins` and lets the newcomer walk to the doorstep. |
| `CollectorPet`, `WorldPetCatalog`, `HaulTally` and `World.Pets.cs` | A pet is a `CollectorPet` of one `CollectorPetKind`. The four collectors' pets count a village collection; the others belong to the world (`World.WorldPets`, the duck first): one for each raw material (ten loads of it tipped out, at a works or a building), each works (ten loads taken in, twenty pieces made) and the bridge, the mill and the tower (their completion; the jetty's is the duck). `HaulTally` (scene-free, saved as `SaveData.Hauls`) counts the loads; `Game.FinishSupplyDump` and `Game.FinishBuildDump` add to it and `Game.EarnPets` announces a pet that has just been earned. A pet waits beside its worker or builder (`World.CreateWorldPets`, called last in `World.Generate`), trails the car in a place of its own (`WorldPetCatalog.Trail`) and is switched off in the garage like the others. A kind is saved by name, so names are never changed. |
| `Glassworks`, `World.PlanGlassworks` | The fourth works (`WorksCatalog.GlassIndex`, `Product.Glass`, `HaulLoad.Glass`, actor ID `ActorIds.Glassworks` = 64) turns sand into glasses. The sand pit's worker sends the sand there (`SourceRole`, `OpenSource`). Every valley with a ford has one: `World.PlanGlassworks` plans it last in `PlanFord`, like the others (the village edge where there is room, else the bank; a field path and yard in `Tracks`), with its own seeded search and without reserving ground in `haulClearings`, so older sites, actors and the plants are generated exactly as before. The plants that stand on its footprint or way are planted all the same and then taken out (`Vegetation.ClearArea`, `World.InGlassworksZone`): `TreePositions` still lists the trees as generated, which keeps the world fingerprints valid, and `NearTrunk` ignores the cleared ones. `World.WorksFor` and `World.AllWorks` reach it, `World.Industry` is still the three original works. Its glasses go to the residents of finished houses: the tenth improvement is followed once by an order for glasses (`Game.HouseMaterial` returns `HaulLoad.Glass`, `Village.IsGlazed`, saved as `VillageSave.Glazed`), paid like a task. |
| `IChallenge` and generators in `Mathematics` and `Letters` | Provide question data, seeded generation and answer validation. |
| `SaveData`, `SaveStore`, `SaveRules`, `SaveMigrations` and `Game.Persistence.cs` | `SaveData` is the save of version 5: the seed, the state and the character met, and one section for each part of the game (`Vehicle`, `Economy`, `Quiz`, `Task`, `Roadside`, `Village`, `Buildings`, `Companions`, `Postcards`, `Events`, `Bandits`), each plain data with defaults, so a file that leaves a section out still loads. `SaveStore` reads and writes the file, falls back to the backup and sets aside copies of what the game could lose (`progress.vN.bak`, `progress.nenacteno-HASH.json`). `SaveRules.All` lists what a save must satisfy, one rule for each part, and `Validate` runs them. `SaveMigrations` moves an older file forward: a file of versions 1 to 4 is read into the flat `SaveDataV4`, which is never changed, goes through the steps to version 4 (one question field, coins instead of car rewards, ten deliveries for each building, one `Trip`) and `ToCurrent` moves it into the sections; `Repair` and `AfterValidation` mend what any version left behind (a damaged ghost record, a house whose task changed, the album that grew, the ten roadside friends). `Game.Persistence.cs` captures and restores the sections. Saved state that is new is a new section, its rule in `SaveRules.All` and its capture and restore; `SaveStore` does not change. Existing numeric `GameState` values and actor IDs are part of the JSON format. |
| `Scripts/Diagnostics` | Launch headless checks, prepare screenshot views and exercise game entry points. `Game` reaches them only through `partial` hooks, and release exports (`ExportRelease`) leave the folder out of the build. |

## Start and game state

`Game._Ready` generates the world, creates the vehicle and camera, initializes the world systems and binds UI events. The diagnostic partial handles command-line modes. Road audit builds the terrain, roads and village. Road-driving checks build the world and vehicle. The other suites and capture views use the initialized game.

`Game` owns the current state and activates the vehicle during exploration. The UI sends intents such as submitting an answer or choosing an expedition. Pause records the previous state. Resume restores its panel, question and selections. Loading a save reuses the same panel restoration.

## Questions and activities

- Add question data and generation alongside the existing quiz types. `Game.Quizzes.cs` selects an enabled type, rotates through language activities and opens the question. `Game.SubmitAnswer` handles answers and forwards successful interactions to the appropriate activity. `GameUi` renders the choices. Keep a new quiz's pending question and partial selections restorable from disk.
- Roadside friends have one opening quiz per world. Solving it unlocks a delivery or apple collection whose choice can be postponed. Cargo handover opens a counting task or, with arithmetic disabled, an enabled language task. Completing that task grants cosmetic choices.
- Village houses draw from seeded schedules of ten tasks (two each of math, letters, fruit, planks and bricks; `VillageTaskKind`). A planks or bricks task is a `HaulTrip` for a `HouseTripTarget` that fetches one unit from the works' stock and tips it in front of the house (`Village.HouseDrop`), in state `HouseMaterialOffer`; it is saved as a `Trip` of kind `house`, validated against the saved schedule, and `SaveStore.MigrateHouseTasks` returns a save that waits at a house whose task changed to driving. Shops, collectors and the sorcerer have their own departure and handover rules. Their active trips use the same `Expedition` slot as roadside trips. Keep checks for opening an activity, completing it and restoring it aligned when adding a new flow.
- Expedition routes follow a graph of existing road samples. Guidance arrows use fixed anchors supplied by `Roads`. Changing position, pickup or destination updates the visible arrows while retaining their road placement.

## Seeded worlds and saves

- `WorldLayout` owns the seeded route and plot plan. `World` generates the village twice on purpose (`World.GenerateVillage`): once to discover the settlement footprint, then, after that area is levelled, again on the levelled ground, before spawning roadside animals; the world fingerprints pin the result. The distances that place benches, signs and roadside friends are named in `WorldTuning`. Use the shared terrain and road measurements when placing new scenery.
- Every actor ID is a number in `ActorIds`, which is the only place that holds them (`World.FarmerId` and the like are aliases), and `World.Register` refuses an ID that is already taken; `contract-checks` holds the numbers and the role of each ID. Register persistent actors in `World.RegisterActors`. The roadside animals use their array indices. Resident IDs start at 30 because older saves reserved 0–29 for roadside animals. The bandit representative has a separate ID (43) and is restored with its encounter in `Game`. The beaver uses 44 and is registered by `World.PlanFord`; the three works' workers use 45–47 and are registered by `World.BuildIndustry`; the builders of the mill, tower and jetty use 48–50 and the workers of the quarry, clay pit and log yard 51–53 and those of their second sites 54–57; the newcomers of the six building plots use 58–63. `PlanFord` searches in passes that start with the original strict rules, so valleys that already had a ford keep it exactly where it was; later passes only add a ford to valleys that had none.
- `World.PlanFord` runs after every older actor and pickup has its place, with its own seeded searches, so existing valleys keep their roads, characters and pickups. The new clearings still remove some trees, and because rejected candidates skip random draws, later tree positions shift. Drivable heights over the bridge and the finished ford come from `World.DriveSurface` and `World.CrossingSurface`.
- `SaveData` contains data only. `Game.Persistence.cs` snapshots the current state, recreates active expeditions and restores cosmetics, progress and panels. When adding persisted fields, supply defaults for older saves and validate the new state in `SaveStore`. Existing numeric `GameState` values and actor IDs are part of the JSON format.
- `SaveStore` validates each candidate before migration, uses the previous backup if the main file is damaged and writes updates through a temporary file. Diagnostic modes, captures and explicit seeds bypass the player save.

## Verifying changes

Run `./build.ps1 -Test` for the headless suite, or `./test.ps1` to run chosen suites and seeds in parallel without rebuilding (`./test.ps1 -List`, `-Suite`, `-Seeds`, `-Build`); both use the same parallel runner in `scripts-common.ps1`, and `CLAUDE.md` asks that it is always used. Add a new diagnostic to `Scripts/Diagnostics` and list it in `Scripts/Diagnostics/DiagnosticSuites.cs` (flag, how to create it, seeds); the game starts it from that list and `build.ps1` reads the list back with `--list-checks`, so nothing else needs to change. `contract-checks` fails when a suite file is missing from the list. Tests that protect saved games are described in `Tests/README.md`. Use `DiagnosticArtifacts.PathFor` for diagnostic files so each parallel run gets its own directory. For persistence changes, exercise a round trip and relevant older save data. For visible changes, run `./run.ps1 -Capture -View <view>` and inspect the image in `artifacts`.
