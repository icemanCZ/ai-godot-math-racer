# Architecture and extension guide

MathRacer is a code-only Godot 4.7.2 .NET project. The root node in `Main.tscn` runs the `Game` script. C# generates the world, illustrations and interface at startup. Player-facing text is Czech.

## Module boundaries

| Module | Responsibility |
| --- | --- |
| `Game` and its feature partials | Compose the scene, handle input and state transitions, coordinate activities and restore the active panel. |
| `ActorRole` and its subclasses (`ActorRoles.cs`) | Give each character one role: roadside friend, house resident, trader, witch, sorcerer or collector (farmer, gardener, gem collector, toymaker). A role picks the `Game` flow for talking to the character and for its solved quiz, and supplies its marker icon and talk hint. Every builder, source and works role has an icon of its own, drawn as a vector outline by `Art.RoleTaskIcon`; sites without a worker (the sand pit, every second site) and the two driving courses put the same kind of icon on a `TaskMarker`. New character types add a role instead of new `Is…` checks in `Game`. |
| `CarRewards` and `RoadsideProgress` | Hold the owned garage items and the player's coins that buy them (prices live on `CarReward`), and which roadside friends have unlocked or finished their expedition. `WorldCoins` scatters collectible coins along the roads; their positions are not saved. `Game` owns one of each and saves them. |
| `GameUi` and its feature partials | Build panels and HUD elements, manage menu focus and emit player intents. |
| `World`, `WorldLayout` and `Village` | Generate seeded routes, plots and interactive actors. `World` registers actors under stable save IDs and exposes them for proximity checks and placement. Names, greetings and colours of recurring characters live in `CharacterCatalog`; its order assigns actor IDs. |
| `LaunchOptions` and `Settings` | `LaunchOptions` is the only reader of the command line. `Settings` holds tuning constants and the only state that outlives a scene reload: the world seed and the quiz settings carried into a new game. |
| `Terrain`, `Roads`, `RoadGrading` and `River` | Provide elevation, road surface and clearance data for meshes, collision, placement, navigation and driving. |
| `Vehicle`, `FollowCamera` and `VehicleAppearance` | Handle movement, camera and cosmetic state. `VehicleModel` shares geometry between gameplay and garage previews. |
| `Expedition` and `DrivingEvents` | Handle cargo and vehicle courses. |
| `RouteGuide` | Plans the road route to one target and owns the road arrows and the final off-road arrow. Expeditions and ford trips each create one. |
| `Trailer`, `Ford`, `BuildProject` and `World.Ford.cs` | The towed trailer follows the car's hitch along `World.DriveSurface` without collision of its own; it is lent for every trip and won as the bridge's reward. `BuildPlans` lists the ten deliveries of each of the four buildings. `BuildProject` holds the stage; `Ford` (the bridge) is one, its deck becomes solid after the tenth. `World.PlanFord` plans the ford, its sand pit, quarry and clay pit and the beaver. `Game.Ford.cs` runs the trips, which share the single task slot with expeditions (`Game.TaskActive`). |
| `HaulTrip`, `Works` and `World.Works.cs` | `HaulTrip` is one trailer trip (source, loading question, drop ring); `BuildTrip` serves a building and `SupplyTrip` a works. `World.PlanIndustry` places the log yard and three `Works` (sawmill, brickworks, gravel works; `WorksCatalog` holds what each takes in and makes). The works first try the village edge (`World.WorksBand`, measured with `Village.PlotDistance`, which the quiet belt around the houses would otherwise forbid) and fall back to passes that relax their spacing, slope and road rules until all fit. `World.PlanExtraSources` then adds a second site for each raw material (`ExtraSources`, at least 110 m from the first); `HaulTrip.Source` is the nearest site when the trip starts and `World.SourceSites` lists them all, so an empty trailer is loaded at whichever one it reaches, and the trip adopts the site it reached. Each second site has a worker (`SourceRole` for the load, IDs 54–57 for stones, soil, sand and logs; the sand pit's worker only asks the bridge's loading question): `World.PickupActor(load, source)` names whoever asks, and `World.AskerIds` lists the IDs a saved loading question may come from. The quarry, clay pit and log yard have workers (`SourceRole`, IDs 51–53) who start supply trips and ask the loading question; each works has a worker (`WorksRole`, IDs 45–47) who shows the stock and loads goods. A stock of up to 12 units is shown one stack or heap per unit. `Works.Take` is how a building takes goods. |
| `SitedProject`, `Mill`, `Lookout`, `Jetty` and `World.Builds.cs` | The mill, lookout tower and jetty are `SitedProject`s: each stands at a `BuildSite` (unloading ring, road point, direction, builder spot) and has ten stage nodes, with solid parts that only block the car once built. `World.PlanBuilds` picks the sites (the tower and mill try the band near the village, `World.LandmarkBand`, preferring high ground and short distance, then anywhere; the jetty a gentle bank) with a way from a road, in passes that allow deeper cuts. `PlanWay` keeps the way within `PathMaxGrade` by cutting it into the slope; `Terrain.Grade` applies the cuts before anything is placed on the terrain, so `PlanFord` plans everything first. Builders (`BuilderRole`, IDs 44 and 48–50) give the work. The special last load comes from a collector, whose quiz loads it (`Game.CompleteChallenge`). `Game.Rewards.cs` holds the completion rewards (coins, the garage items from `CarAccessory.FlourSack`, `CarAccessory.Binoculars` and `CarLook.Water`, the baker's bonus and the mill's sails); `Game.Lookout.cs` the look from the tower (`FollowCamera.ShowPanorama`, `WorldCoins.Flash`, `Animal.Ping`); `Boat` the jetty's boat. The jetty's duck is a `CollectorPet` of kind `Duck` owned by the world (`World.Duck`, `World.AllPets`), whose count is the jetty's stage. |
| `HousePlot`, `PlotPlans`, `PlotTrip` and `Village.Plots.cs` | The village has six building plots (`PlotPlans.Count`). `Village.GeneratePlots` runs last, after the square and before the architectural details, so the rest of the village keeps its old positions: it lists lots beside every road, nearest to the village centre first, takes the first six that are clear (`PlotIsClear`: off roads and the river, clear of everything reserved so far and of the roadside benches and signs) and reserves it (`IsReserved`, so trees and later placement avoid it). It tries ground inside the village's existing terrain platform first and leaves the shared `plots` list alone, so the platform and the search for the works and landmarks are unchanged. `HousePlot` is one lot: a staked-out site with a newcomer (`PlotResidentRole`, actor IDs from `World.FirstPlotResidentId`, `CharacterCatalog.PlotResidents`) and six stage nodes (slab, lower walls, upper walls, roof frame, roof, finishing), with solid parts that block the car once built. `PlotPlans.CargoOf` lists the six loads (gravel, two of bricks, three of planks), always goods from a works. A `PlotTrip` is a `HaulTrip` whose drop ring lies in front of the lot, on a walkway to the street; `Game.Plots.cs` runs it in state `PlotStatus`, shares the task slot with the other trailer trips, sends the player for raw material when the works is empty (`BeginMissingSupply`) and, after the sixth load, pays `PlotCoins` and lets the newcomer walk to the doorstep. |
| `IChallenge` and generators in `Mathematics` and `Letters` | Provide question data, seeded generation and answer validation. |
| `SaveData`, `SaveStore` and `Game.Persistence.cs` | Define the JSON data, validate and migrate it, and translate between data and live scene state. Building progress is `BuildStages` (four numbers, 0–10) and the plots' is `PlotStages` (six numbers, 0–6, with `PlotTrip` for a trip under way; saves from before the plots load with empty plots); saves from the six-load bridge are migrated on load (a finished bridge stays finished, a trip under way is dropped). Save version 3 stores coins; version 2 saves with an open reward choice are migrated to the delivery's coins. Version 2 introduced the single `Challenge` field tagged with `$type`; version 1 saves are migrated on load. |
| `Scripts/Diagnostics` | Launch headless checks, prepare screenshot views and exercise game entry points. `Game` reaches them only through `partial` hooks, and release exports (`ExportRelease`) leave the folder out of the build. |

## Start and game state

`Game._Ready` generates the world, creates the vehicle and camera, initializes the world systems and binds UI events. The diagnostic partial handles command-line modes. Road audit builds the terrain, roads and village. Road-driving checks build the world and vehicle. The other suites and capture views use the initialized game.

`Game` owns the current state and activates the vehicle during exploration. The UI sends intents such as submitting an answer or choosing an expedition. Pause records the previous state. Resume restores its panel, question and selections. Loading a save reuses the same panel restoration.

## Questions and activities

- Add question data and generation alongside the existing quiz types. `Game.Quizzes.cs` selects an enabled type, rotates through language activities and opens the question. `Game.SubmitAnswer` handles answers and forwards successful interactions to the appropriate activity. `GameUi` renders the choices. Keep a new quiz's pending question and partial selections restorable from disk.
- Roadside friends have one opening quiz per world. Solving it unlocks a delivery or apple collection whose choice can be postponed. Cargo handover opens a counting task or, with arithmetic disabled, an enabled language task. Completing that task grants cosmetic choices.
- Village houses draw from seeded schedules of ten tasks (two each of math, letters, fruit, planks and bricks; `VillageTaskKind`). A planks or bricks task is a `HouseTrip`, a `HaulTrip` that fetches one unit from the works' stock and tips it in front of the house (`Village.HouseDrop`), in state `HouseMaterialOffer`; its save fields are `HouseTrip` and `HouseTripLoaded`, validated against the saved schedule, and `SaveStore.MigrateHouseTasks` returns a save that waits at a house whose task changed to driving. Shops, collectors and the sorcerer have their own departure and handover rules. Their active trips use the same `Expedition` slot as roadside trips. Keep checks for opening an activity, completing it and restoring it aligned when adding a new flow.
- Expedition routes follow a graph of existing road samples. Guidance arrows use fixed anchors supplied by `Roads`. Changing position, pickup or destination updates the visible arrows while retaining their road placement.

## Seeded worlds and saves

- `WorldLayout` owns the seeded route and plot plan. `World` generates the village once to discover the settlement footprint, levels that area, then rebuilds the roads and village before spawning roadside animals. Use the shared terrain and road measurements when placing new scenery.
- Every actor ID is a number in `ActorIds`, which is the only place that holds them (`World.FarmerId` and the like are aliases), and `World.Register` refuses an ID that is already taken; `contract-checks` holds the numbers and the role of each ID. Register persistent actors in `World.RegisterActors`. The roadside animals use their array indices. Resident IDs start at 30 because older saves reserved 0–29 for roadside animals. The bandit representative has a separate ID (43) and is restored with its encounter in `Game`. The beaver uses 44 and is registered by `World.PlanFord`; the three works' workers use 45–47 and are registered by `World.BuildIndustry`; the builders of the mill, tower and jetty use 48–50 and the workers of the quarry, clay pit and log yard 51–53 and those of their second sites 54–57; the newcomers of the six building plots use 58–63. `PlanFord` searches in passes that start with the original strict rules, so valleys that already had a ford keep it exactly where it was; later passes only add a ford to valleys that had none.
- `World.PlanFord` runs after every older actor and pickup has its place, with its own seeded searches, so existing valleys keep their roads, characters and pickups. The new clearings still remove some trees, and because rejected candidates skip random draws, later tree positions shift. Drivable heights over the bridge and the finished ford come from `World.DriveSurface` and `World.CrossingSurface`.
- `SaveData` contains data only. `Game.Persistence.cs` snapshots the current state, recreates active expeditions and restores cosmetics, progress and panels. When adding persisted fields, supply defaults for older saves and validate the new state in `SaveStore`. Existing numeric `GameState` values and actor IDs are part of the JSON format.
- `SaveStore` validates each candidate before migration, uses the previous backup if the main file is damaged and writes updates through a temporary file. Diagnostic modes, captures and explicit seeds bypass the player save.

## Verifying changes

Run `./build.ps1 -Test` for the headless suite. Add a new diagnostic to `Scripts/Diagnostics` and list it in `Scripts/Diagnostics/DiagnosticSuites.cs` (flag, how to create it, seeds); the game starts it from that list and `build.ps1` reads the list back with `--list-checks`, so nothing else needs to change. `contract-checks` fails when a suite file is missing from the list. Tests that protect saved games are described in `Tests/README.md`. Use `DiagnosticArtifacts.PathFor` for diagnostic files so each parallel run gets its own directory. For persistence changes, exercise a round trip and relevant older save data. For visible changes, run `./run.ps1 -Capture -View <view>` and inspect the image in `artifacts`.
